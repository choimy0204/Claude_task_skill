# tiered-dispatch 벤치마크

플러그인과 메인 모델 구성이 "같은 사용량으로 얼마나 많은 작업을 하는지"를 비교하는 고정 벤치마크.
결과 원표: [results/summary.md](results/summary.md)

## 한계 (먼저 읽기)
- 금액은 `claude -p` 결과의 토큰 사용량을 **API 가격으로 환산**한 값이다. Pro·Max 요금제 한도는 달러로 공개되지 않으므로 구성 간 **비율**로만 해석한다.
- 대부분 과제당 1회 측정이다. B1은 Sonnet 두 구성을 3회씩 반복했고 회차 편차가 ±25% 정도였다. 10~20% 차이는 잡음일 수 있다.
- 과제 5개는 한 사람의 작업 유형(C# 저장소 탐색, Python 기능 추가·버그 수정)에 맞춘 것이다.

## 과제
| 과제 | 내용 | 채점 |
|---|---|---|
| B1 | 실제 대형 C# 저장소의 처리 흐름 분석 (읽기 전용, `--disallowedTools "Edit Write NotebookEdit"`) | 핵심 식별자 15개 언급 수, `.cs:줄` 인용 수, 원본 무변경 |
| B2 | 버그 수정 (fixture) | 기존 테스트 통과, 테스트 파일 무변경 |
| B3 | 기능 추가: 반품 | 숨은 테스트 7개 |
| B4 | 한 세션에서 4개 주제 연속 (로그 분석 → 버그 → 기능 → 앞 내용 회상) | 턴별 숨은 테스트·정답 |
| B5 | 독립 모듈 4개 신규 구현 (나눌 수 있는 큰 구현) | 숨은 테스트 6개, 테스트 파일 4개 |

- fixture: `fixture/` (orderdesk, Python 표준 라이브러리만 사용). 정답 구현 `hidden/reference.py`로 숨은 테스트가 풀리는 문제인지 확인했다.
- B1 대상 저장소 경로와 채점 키워드는 공개하지 않는다: `local/b1.json` `{ "repo": ..., "keywords": [...] }` (git 제외).

결론과 v2.5.0 반영:
1. **메인을 Sonnet으로** 두는 것이 가장 크다: Opus 대비 약 2.4배. (플러그인 밖의 사용자 설정)
2. Sonnet 메인은 위임해도 이득이 없다: 탐색 Haiku 위임은 비용 같고 품질 약간 낮음, 병렬 구현은 스스로 쓰지 않았고 단독이 가장 쌌다. → v2.5.0: Sonnet·Haiku 메인은 위임하지 않음.
3. Opus 메인에서 플러그인: 탐색 −25%, 여러 주제 세션 −16%. 병렬 구현은 비용 +35%, 시간 −40%.
4. 서브에이전트 도구 목록 제한: 에이전트당 고정 비용 −70% (MCP 도구 정의가 빠짐). → v2.5.0 반영.
5. opusplan은 계획 단계 Opus 비용이 더해져 기능 작업(B3, B4)에서 가장 비쌌다. → 채택 안 함.
6. Opus 자문(advisor)은 Sonnet 메인에서 한 번도 호출되지 않아 효과를 확인할 수 없었다. → 넣지 않음.

- 벤치 과제에서는 v2.6 기능이 작동할 일이 없었다: 모델이 파일을 Read 대신 Bash `cat`으로 읽어 Read 가드가 한 번도 걸리지 않았고, 컨텍스트가 90k 이하라 자동 압축·Bash 출력 상한과도 무관. 차이는 실행 간 편차 범위(B4 Opus 3회씩 비교에서 확인).
- v2.6의 효과는 긴 실사용 세션 기준이다: 과거 기록 분석(`tools/cost_breakdown.js`, `ctx_composition.js`, `compact_sim.js`)에서 200k 자동 압축 상한 추정 Sonnet −57%, Opus −41%. Read 결과가 Sonnet 메인 컨텍스트 증가분의 20%, 캐시 만료 뒤 재작성이 비용의 약 9%.
- 훅 지연: guard-read·idle-notice 각 약 0.4초(PowerShell 시작 비용). Read 1회·프롬프트 1회마다 발생.

## 긴 세션: /clear 효과 (오프라인 분석)
`tools/clear_sim.js`가 `~/.claude/projects`의 과거 기록을 읽어 숫자만 낸다 (본문 출력 없음, 모델 호출 없음).
앞 활동과 N분 이상 떨어진 사용자 입력을 주제 경계로 보고, 그때 /clear 했다면 이후 호출에서 빠졌을 컨텍스트 비용을 계산한다.
새 대화에서 필요한 내용을 다시 읽는 비용이 있으므로 상한의 절반을 현실적인 값으로 본다.

- 74개 세션(호출 30회 이상), $4,966 중 절약 상한 35~48%, 절반 반영 **약 17~24%**.
- 경계 시점 컨텍스트 중앙값 344k. 과거 세션은 900k~1M까지 커졌다.
- 모델 규칙("주제가 끝나면 /clear 권장")만으로는 B4에서 한 번도 문구가 나오지 않았다(모델은 자기 컨텍스트 크기를 모른다). → v2.5.0: Stop 훅이 컨텍스트 120k를 넘을 때 한 번, 이후 100k마다 한 번 권장 문구를 띄운다 (모델 토큰 0).

## 실행
```
export BENCH_WORK=<작업 복사본 폴더>
bash tools/run.sh <구성> <과제> <태그>      # 예: bash tools/run.sh C B5 r1
node tools/summary.js [이름 필터]
node tools/clear_sim.js [최소 호출 수]
```
- 원자료는 `results/raw/<과제>_<구성>_<태그>/`에 쌓이며 git에 올리지 않는다(실제 저장소 분석 내용 포함).
- 실행 중에는 tiered-dispatch·design-lean·headroom 설치 플러그인을 `--settings`로 끄고, 비교 대상 플러그인만 `--plugin-dir`로 넣는다.
- 비용: `total_cost_usd`는 같은 세션의 `--resume` 호출에서 누적되므로 세션별 최댓값을 쓴다.
