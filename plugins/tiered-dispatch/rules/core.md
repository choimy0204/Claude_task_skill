# tiered-dispatch 작업 분배 규칙
작업 규모와 메인 모델로 판단한다. Haiku 서브에이전트는 탐색 1건에 약 $0.03이라 위임 비용은 거의 메인 몫(지시 작성·결과 읽기·대기 시간)이다. 메인이 직접 읽을 양이 지시와 결과보다 훨씬 클 때만 위임한다. (실측: Opus 메인 큰 탐색 −25%. 작은 작업은 위임하면 느리고 메인 비용도 줄지 않았다.)

## 메인 모델별 기준 (시스템에 안내된 현재 세션 모델)
- Opus: 아래 1·2번과 simple-worker를 모두 쓴다. 메인 단가가 높으니 큰 탐색 기준은 "파일 20개 이상"으로 본다.
- Sonnet: 1번(큰 탐색)과 simple-worker만 쓴다. 큰 탐색 기준은 "파일 수십 개 이상". 구현은 직접 한다(implementer도 Sonnet이라 이득이 없다).
- Haiku: 위임하지 않는다.

## 위임하는 경우
1. 큰 탐색·분석 → tiered-dispatch:code-searcher (haiku), 병렬
   - 저장소 전체 분석, 구조 파악, 여러 모듈에 걸친 흐름 추적, 위 기준 이상의 파일을 읽어야 하는 조사, 수천 줄 넘는 로그 분석
   - 파일 목록 명령 1~2번으로 관련 파일이 몇 개로 좁혀지면 위임하지 않고 직접 읽는다.
   - 순서: ① 파일 목록 명령 1번: `git ls-files | awk -F/ '{print $1"/"$2}' | sort | uniq -c | sort -rn | head -40` (확장자 필터만 바꿔 쓴다. 실패하거나 부족해도 다시 돌리지 말고 그 결과로 나눈다) → ② 바로 폴더·모듈·주제 단위로 나눠 code-searcher 병렬 호출 → ③ 최종 답변. 메인 호출은 이 3번이 목표다. 사이에 Read·Bash·확인 명령을 넣지 않는다. 결과를 받은 뒤에도 메인은 원본을 열지 않는다. 분배 계획은 길게 고민하지 않고 폴더별 줄 수로 바로 나눈다.
   - ②를 하기 전에 소스·설정·프로젝트 파일(.cs, .csproj, .sln 등)의 내용을 메인이 직접 읽지 않는다. 범위를 완벽하게 나누려 하지 않는다. 겹치거나 빠진 부분은 결과를 받고 보완한다.
   - 에이전트는 최대 4개로 나눈다. 에이전트가 늘면 메인이 지시를 쓰고 결과를 읽는 비용이 늘어난다(실측: 6~8개로 늘리면 메인 비용 +50~60%). 범위가 겹치지 않게 나눈다.
   - 프롬프트는 3~5줄: 목표 한 줄, 범위 경로, 찾을 것, 제외할 것. 보고 형식·확인 방법은 code-searcher 정의에 있으니 쓰지 않는다. 모든 에이전트에 같은 문장을 쓰고 범위만 바꾼다.
2. 크고 나눌 수 있는 구현 → tiered-dispatch:implementer (sonnet), 병렬 (Opus 메인만)
   - 서로 독립적인 파일 묶음 3개 이상으로 나눌 수 있는 구현·테스트 작성·리팩터링
   - 변경 파일이 겹치지 않게 나눈다. 겹치면 메인이 직접 한다.
- 판단이 필요 없는 기계 작업(파일 10개 이상의 포맷·이름 변경, 명령 실행 후 긴 출력 요약)은 tiered-dispatch:simple-worker (haiku).
- 그 밖의 작업(파일 몇 개 수정, 좁은 탐색·디버깅, 짧은 로그 분석, 설명)은 메인이 직접 한다.
- 코드 탐색에 내장 Explore·general-purpose 에이전트를 쓰지 않는다. 메인 모델로 돌고 도구 목록이 커서 비싸다(실측 호출당 $0.3~2.5, code-searcher는 $0.01~0.03). 탐색은 위 기준대로 code-searcher 또는 메인이 직접 한다.
- 호출할 때 model 파라미터(haiku / sonnet)를 항상 명시한다.

## 위임할 때
- 한 메시지에서 병렬로 호출하고 `run_in_background: false`로 둔다. 결과가 한 번에 돌아와 턴이 준다(백그라운드로 두면 완료 알림마다 메인 턴이 하나씩 늘어 전체 컨텍스트를 다시 읽는다).
- 직전에 한 줄 알린다: `[분배] <작업> → <에이전트>(<모델>)×N · 가정: <판단 근거>`
- 서브에이전트는 대화 맥락을 모른다. 프롬프트에 목표, 범위(경로), 결정사항, 완료 기준, 그리고 대화에서 알게 된 주의점을 적는다. 지시가 매우 길면 handoff 스킬로 md 지시서를 쓴다.
- 호출한 뒤에는 결과를 기다린다. 기다리는 동안 명령·파일 읽기·중간 안내 문장·예약(ScheduleWakeup)을 하지 않는다.
- 서브에이전트가 확인한 결과는 그대로 쓴다. 메인이 원본을 다시 열어 재확인하지 않는다.
- 결과를 검토하고, 가능하면 빌드·테스트를 돌리고, 원래 요청과 맞는지 대조한다. 작은 보완은 직접 고친다.

## 메인 토큰 절약 (항상)
메인 비용의 대부분은 "컨텍스트 크기 × 턴 수"다. 한 번 들어온 도구 출력은 이후 모든 턴에서 다시 읽힌다.
- 턴을 줄인다: 서로 독립적인 명령·파일 읽기·검색은 한 메시지에 묶어서 호출한다. 한 번에 하나씩 확인하며 진행하지 않는다.
- 출력을 작게 받는다: 목록은 개수·요약(폴더별 개수, grep -c, head 제한)으로 보고, 파일은 필요한 줄 범위만 읽는다(Read의 offset/limit, grep -n 후 해당 부분). 수백 줄짜리 목록·로그·파일 전체를 컨텍스트에 붓지 않는다.
- 같은 파일을 다시 읽지 않는다. 이미 본 내용은 기억한 것을 쓴다.
- 기존 파일 수정은 Edit으로 바뀌는 부분만 보낸다. 전체를 다시 쓰는 Write는 새 파일이나 대부분을 바꿀 때만 쓴다. (쓴 내용도 이후 모든 턴에 남는다)
- 최종 답변은 결과·변경점·남은 문제 위주로 짧게 쓴다. 이미 보여준 코드·출력을 다시 옮기지 않는다. 문제·개선점 탐색 결과는 영향 큰 순 표 하나(열: 경로:줄 | 문제 | 방향 | 영향, 칸마다 짧은 구절)와 총평 2줄로 쓴다. 에이전트가 확인한 항목은 중복만 합치고 빠짐없이 한 줄씩 넣는다. 서론·범위 설명·반복 설명을 붙이지 않는다.

## 확인이 필요한 경우 (위임 여부와 무관)
방법이 여러 가지이고 결과가 크게 달라질 때 / 구조 변경(모듈 구조, 공개 API, DB 스키마, 설정 형식) / 삭제·대량 이름 변경 / 요청 해석이 두 가지 이상일 때는 먼저 사용자에게 확인한다.

## 기록
- 에이전트·모델·토큰 사용량은 훅이 자동으로 기록한다. 담당 표를 따로 만들지 않는다.
- 작업을 처리한 응답 끝에는 항상 한 줄을 붙인다. 짧은 질문·대화에는 붙이지 않는다.
  위임했을 때: `처리: main(opus) · 위임: code-searcher(haiku)×8`
  혼자 처리했을 때: `처리: main(opus)`
  main 모델은 시스템에 안내된 현재 세션 모델을 opus / sonnet / haiku로 적는다. 알 수 없으면 `main(확인 안 됨)`.
- 커밋은 담당 단위로 나누고, 본문에 `Agent: 이름 (모델)`을 적는다. 모델은 호출할 때 넣은 model 값을 따른다.
- 사용량이나 절약 효과를 물으면 usage-report 스킬을 쓴다.
