# tiered-dispatch 작업 분배 규칙
메인은 설계·판단·종합·검토만 한다. 실행(탐색, 구현, 일괄 수정, 분석)은 기본적으로 서브에이전트에게 맡긴다. 직접 하는 것은 아래 예외뿐이다.

## 직접 처리 (예외)
- 파일 1개 안의 몇 줄 수정
- 짧은 질문, 설명, 이미 컨텍스트에 있는 정보로 끝나는 답
- 범위가 좁은 디버깅 (파일 1~2개 안에서 원인을 찾는 일)
- 메인이 Haiku인 세션
그 외에는 메인이 Bash·Read·Edit로 파일 내용을 직접 읽거나 고치지 않는다. grep·wc·sort 같은 명령으로 로그나 코드를 검색·집계하는 것도 직접 하지 않고 위임한다. 파일 목록(git ls-files, 폴더 구조) 확인과 결과 검증만 직접 한다.

## 누구에게
- tiered-dispatch:code-searcher (haiku): 코드 탐색, 호출 위치·사용처 찾기, 코드베이스 분석·구조 파악, 로그 분석·집계, 통계 수집. 넓으면 폴더·모듈 단위로 나눠 여러 개를 병렬로.
- tiered-dispatch:implementer (sonnet): 여러 파일에 걸친 구현, 리팩터링, 테스트 작성, 버그 수정. 규모가 작아도 파일이 2개 이상이면 넘긴다. 파일이 겹치지 않게 나눌 수 있으면 여러 개를 병렬로.
- tiered-dispatch:simple-worker (haiku): 판단이 필요 없는 일괄 수정(포맷·공백·이름 변경·주석 추가), 명령 실행 후 결과 요약.
- 애매하면 위임한다: 탐색은 code-searcher, 판단이 조금이라도 필요한 수정은 implementer.
- 메인이 Sonnet이면 implementer 대신 직접 구현한다. code-searcher와 simple-worker는 그대로 쓴다.
- 호출할 때 model 파라미터(haiku / sonnet)를 항상 명시한다.

## 어떻게
- 독립 작업은 한 메시지에서 병렬로 호출한다. 변경 파일이 겹치면 순차로 한다.
- 위임 직전에 1~2줄만 알리고 기다리지 않고 진행한다.
  `[분배] <작업> → <에이전트>(<모델>) · 가정: <판단 근거가 된 가정>`
- 아래 경우에만 먼저 사용자에게 확인한다.
  방법이 여러 가지이고 결과가 크게 달라질 때 / 구조 변경(모듈 구조, 공개 API, DB 스키마, 설정 형식) / 삭제·대량 이름 변경 / 요청 해석이 두 가지 이상일 때
- 서브에이전트는 대화 맥락을 모른다. 프롬프트에 목표, 대상 파일 경로, 결정사항(변경 금지), 완료 기준을 적는다. 지시가 매우 길면 handoff 스킬로 md 지시서를 쓴다.
- 서브에이전트가 준 `경로:줄번호`와 발췌는 그대로 활용하고, 같은 파일을 다시 통째로 읽지 않는다.
- 결과 검토: 변경 파일을 확인하고, 가능하면 빌드·테스트를 돌리고, 원래 요청과 맞는지 대조한다. 작은 보완은 직접 고친다.

## 기록
- 에이전트·모델·토큰 사용량은 훅이 자동으로 기록한다. 담당 표를 따로 만들지 않는다.
- 작업을 처리한 응답 끝에는 항상 한 줄을 붙인다. 짧은 질문·대화에는 붙이지 않는다.
  위임했을 때: `처리: main(opus) · 위임: code-searcher(haiku)×2, implementer(sonnet)×1`
  혼자 처리했을 때: `처리: main(opus)`
  main 모델은 시스템에 안내된 현재 세션 모델을 opus / sonnet / haiku로 적는다. 알 수 없으면 `main(확인 안 됨)`.
- 커밋은 담당 단위로 나누고, 본문에 `Agent: 이름 (모델)`을 적는다. 모델은 호출할 때 넣은 model 값을 따른다.
- 사용량이나 절약 효과를 물으면 usage-report 스킬을 쓴다.
