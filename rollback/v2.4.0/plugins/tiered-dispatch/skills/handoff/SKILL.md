# 핸드오프 지시서

분배 기준과 진행 방식은 세션 시작 시 주입된 tiered-dispatch 규칙을 따른다. 이 스킬은 **지시서가 필요한 큰 작업**에만 쓴다.

## 언제 md로 쓰나
- 수정 파일이 많고, 파일마다 작업 내용이 달라 프롬프트가 길어질 때
- 여러 에이전트에게 나눠 넘기면서 공통 결정사항을 공유해야 할 때
- 작업 기록을 저장소에 남겨야 할 때

그 외에는 프롬프트에 목표, 대상 파일, 결정사항, 완료 기준을 짧게 적어 바로 넘긴다. md 작성은 메인 모델의 출력 토큰을 쓰기 때문이다.

## 작성 규칙
- 위치: 프로젝트 루트 `handoff/YYYY-MM-DD_작업명.md`
- 서브에이전트는 대화를 모른다. md만 보고 일할 수 있어야 한다.
- 파일 경로는 프로젝트 루트 기준으로 정확히 적는다. 수정할 클래스·함수·대략적인 위치까지 적어서 서브에이전트가 코드베이스를 뒤지지 않게 한다.
- 이미 정한 것은 "결정사항 (변경 금지)"에 적어 다시 고민하지 않게 한다.
- 완료 기준은 확인 가능한 형태로 적는다. (예: "빌드 에러 없음", "샘플 입력에 대해 X 출력")
- 짧게 쓴다. 필요 없는 섹션은 지운다.
- 여러 에이전트에게 나눌 때는 공통 부분을 한 md에 두고, 에이전트별로 "담당 범위"를 나눠 적는다. 변경 파일이 겹치지 않게 나눈다.

호출 프롬프트는 짧게: `handoff/2026-09-28_log-filter.md 를 읽고 그대로 작업해.`

## 템플릿

```markdown
# 작업: <작업명>

## 목표
- <한두 줄>

## 배경 (필요한 만큼만)
- <서브에이전트가 알아야 할 맥락>

## 결정사항 (변경 금지)
- <언어, 라이브러리, 구조, 인코딩 등>

## 수정/생성할 파일
- `<경로>` : <신규 / 수정 - 어떤 부분>

## 구체 작업
1. <파일, 함수 단위로>

## 건드리지 말 것
- <수정하면 안 되는 파일이나 영역>

## 완료 기준
- <확인 가능한 조건>

## 막히면
- 추측해서 진행하지 말고 멈춘 뒤, 무엇이 불명확한지 보고할 것
```
